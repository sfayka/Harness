# KNO-183 Proof Bundle: PR create read-back reconciliation hardening

## Scope

This proof validates the current `main` behavior for missing-PR reconciliation hardening where Harness must not trust only the synchronous GitHub PR create response.

Validated scenarios:

- **Scenario A**: create response succeeds and persisted read-back remains valid for current run.
- **Scenario B**: create response succeeds but persisted read-back is not visible.
- **Scenario C**: create response succeeds, persisted read-back exists, but fails current-run validation.

This is a **local controlled execution** proof run using `HarnessApiService` with deterministic fake GitHub gateway behavior (same fixture approach used by reconciliation unit tests). Hosted proof was not produced in this run.

## How the scenarios were constructed

Artifacts were generated by:

```bash
PYTHONPATH=. python docs/demo/kno-183-pr-create-readback-validation/generate_proof_bundle.py
```

Scenario construction details:

- **A**: `_FakeGitHubGateway(created_pr=_pull_request(number=631))`
  - create response returns PR 631
  - persisted `get_pull_request` returns matching PR facts
  - expected: revalidation passes, artifact attached, task can complete
- **B**: `_FakeGitHubGateway(created_pr=_pull_request(number=632), persisted_created_pr=None)`
  - create response returns PR 632
  - persisted read-back returns `None`
  - expected: revalidation fails, no trusted created proof, reconciliation fails/escalates
- **C**: `_FakeGitHubGateway(created_pr=_pull_request(number=633), persisted_created_pr=_pull_request(number=633, head_sha="111..."))`
  - create response returns PR 633
  - persisted read-back exists but with wrong head SHA
  - expected: persisted PR rejected, reconciliation fails/escalates
